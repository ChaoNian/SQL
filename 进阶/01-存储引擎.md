# 01 · 存储引擎

## 目标

理解「存储引擎」是什么，能对比 InnoDB / MyISAM，会查看与修改表引擎，知道选型直觉。

## 大纲

### 1. 什么是存储引擎

- MySQL 的架构：连接层 / SQL 层 / 存储引擎层  
- 引擎负责：数据如何存、如何索引、是否支持事务/外键/行锁  
- 同一实例可对不同表使用不同引擎
存储引擎就是存储数据、建立索引、更新/查询数据等技术的实现方式。存储引擎是基于表的，而不是基于库的所以存储引擎也可被称为表类型；
连接层
 最上层是一些客户端和链接服务，主要完成一些类似于链接处理、授权认证、及相关的安全方案，服务器也会为安全接入的每一个客户端验证它所具有的操作权限

服务层
 第二层架构主要完成大多数的核心服务功能，如SQL接口，并完成缓存的查询，SQL的分析和优化，部分内置含税的执行，所有跨存储引擎的功能也在这一层实现，如过程、函数等；

 引擎层
 储存引擎真正的负责了MySQL中数据的存储和提取，服务器通过API和存储引擎进行通信，不同的存储引擎具有不同的功能，这样我们可以根据自己的需要，来选取合适的存储引擎。

 存储层
 主要将数据存储在文件系统之上，并完成与存储引擎的交互；


### 2. 查看与设置

```sql
-- 查看支持的引擎
SHOW ENGINES;

-- 查看某表引擎
SHOW CREATE TABLE emp\G
SELECT TABLE_NAME, ENGINE FROM information_schema.TABLES
WHERE TABLE_SCHEMA = 'demo';

-- 建表指定 / 修改引擎
CREATE TABLE t (...) ENGINE = InnoDB;
ALTER TABLE t ENGINE = InnoDB;
```

### 3. 常见引擎对比

#### 存储引擎特点

| 特点 | InnoDB | MyISAM | Memory |
|------|--------|--------|--------|
| 存储限制 | 64TB | 有 | 有 |
| 事务安全 | 支持 | — | — |
| 锁机制 | 行锁 | 表锁 | 表锁 |
| B+tree 索引 | 支持 | 支持 | 支持 |
| Hash 索引 | — | — | 支持 |
| 全文索引 | 支持（5.6 后） | 支持 | — |
| 空间使用 | 高 | 低 | N/A |
| 内存使用 | 高 | 低 | 中等 |
| 批量插入速度 | 低 | 高 | 高 |
| 支持外键 | 支持 | — | — |

#### InnoDB

- **介绍**：兼顾可靠性与高性能的通用存储引擎；MySQL 5.5 之后为默认引擎  
- **特点**：
  - DML 遵循 ACID，支持事务  
  - 行级锁，提高并发访问性能  
  - 支持外键 `FOREIGN KEY`，保证完整性  
- **文件**：`xxx.ibd`（`xxx` 为表名）——每张表一个表空间，存表结构（frm/sdi）、数据与索引  
- **参数**：`innodb_file_per_table`

#### MyISAM

- **介绍**：MySQL 早期默认存储引擎  
- **特点**：
  - 不支持事务、不支持外键  
  - 表锁，不支持行锁  
  - 访问 / 批量插入较快  
- **文件**：
  - `xxx.sdi`：表结构  
  - `xxx.MYD`：数据  
  - `xxx.MYI`：索引  

#### Memory

- **介绍**：表数据存在内存中；受断电等影响会丢数据，适合临时表或缓存  
- **特点**：内存存放；默认 Hash 索引  
- **文件**：`xxx.sdi`（表结构）

### 4. 其他引擎（了解）

- `CSV` / `ARCHIVE`：特殊存储，按需了解  
- 默认引擎：`default_storage_engine`（现多为 InnoDB）

### 5. 按业务选型

按**业务怎么用数据**选，别先纠结引擎名字。拿不准就用 **InnoDB**。

#### 先问自己 4 个问题

1. 要不要「要么全成、要么全败」？（下单、扣款、转账）  
2. 会不会很多人同时改不同行？（秒杀、多人编辑）  
3. 数据能不能丢？（掉电、重启后还在不在）  
4. 是长期业务表，还是临时算一下？

#### 对照表

| 业务特征 | 更合适 | 原因（白话） |
|----------|--------|--------------|
| 下单、库存、支付、账号 | **InnoDB** | 要事务 + 行锁，别人改李四不影响你改张三 |
| 多数系统的默认业务表 | **InnoDB** | 现在默认就是它，省心 |
| 只要外键、强一致关联 | **InnoDB** | 另外两个基本不支持外键 |
| 临时结果、会话缓存、重启可丢 | **Memory** | 数据在内存，快，但断电没了 |
| 几乎只读、很少再改的历史归档（老项目） | 可考虑 MyISAM | 表锁、批量插入快；**新项目一般不选** |

#### 三个业务小案例

- **电商下单**：扣库存 + 写订单必须一起成功 → **InnoDB**（事务）。用 MyISAM 扣了库存却没写成订单，很难自动回滚。  
- **多人同时改各自资料**：每人改自己那一行 → **InnoDB 行锁**。表锁引擎会变成「全世界排队改一张表」。  
- **报表临时汇总**：算完用一下，挂了重算就行 → 可用 **Memory**（或临时表）；别把订单、用户主数据放 Memory。

#### 选型口诀

- **钱、库存、用户主数据、要回滚** → InnoDB  
- **临时、可丢、要极致内存速度** → Memory（慎用，注意内存上限）  
- **MyISAM** → 维护老库时认识即可；**新业务别当首选**  
- 改引擎有成本（重建表），生产慎用  

> 引擎选定后，表结构、索引、事务边界，往往比「纠结 MyISAM 还是 InnoDB」更影响业务效果。

## 小结

- 引擎决定「表怎么存、能不能事务、锁多细」  
- 现代 MySQL 以 InnoDB 为主；按业务选型，拿不准就用 InnoDB  
- `SHOW ENGINES` / `SHOW CREATE TABLE` 可确认现状

## 常见坑 / 面试点

- 「MySQL 有没有事务」要看引擎，不是笼统回答  
- 从 MyISAM 迁 InnoDB 时注意外键、自增、全文索引差异  
- 面试：InnoDB vs MyISAM 核心差异表
