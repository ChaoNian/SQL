# 03 · SQL 优化

## 目标

能用 `EXPLAIN` 看懂执行计划关键字段，定位慢查询常见原因，掌握一批「可落地」的改写手段。

## 大纲

### 1. 优化层次

- SQL 与索引（本篇重点）  
- 表结构 / 范式与反范式  
- 引擎与参数、硬件与架构（缓存、读写分离等，后文/运维）

### 2. 慢查询入门

- 打开慢日志思路：`slow_query_log`、`long_query_time`  
- 先找「最慢 / 最频繁」的语句，再分析

### 3. EXPLAIN 关键字段

```sql
EXPLAIN SELECT ...;
-- MySQL 8.0 也可：EXPLAIN ANALYZE SELECT ...;
```

优先看：

| 字段 | 关注点 |
|------|--------|
| `type` | `ALL` 差；`ref` / `range` / `const` 较好 |
| `key` | 实际用到的索引 |
| `rows` | 预估扫描行数 |
| `Extra` | `Using filesort` / `Using temporary` / `Using index` |

### 4. 常见问题与改写

- 索引失效：函数包列、隐式转换、`OR` 滥用、违背最左前缀  
- 只查需要的列；慎用 `SELECT *`（尤其大宽表）  
- 深分页：`LIMIT 100000, 10` → 延迟关联 / 记上次最大 id  
- `COUNT(*)` 与近似统计（了解业务能否接受近似）  
- JOIN：小结果集驱动；保证连接列类型一致、有索引

### 5. 优化检查清单（实操顺序）

1. 业务是否必须这么查  
2. 有没有合适索引、是否用上（`EXPLAIN`）  
3. SQL 能否改写（条件、分页、子查询 ↔ JOIN）  
4. 表结构是否合理（冗余字段、拆表）  
5. 再考虑缓存 / 架构

## 小结

- 优化从「可测量」开始：慢日志 + `EXPLAIN`  
- 多数慢查询是索引与写法问题，不是先调参  
- 改完要复测，避免凭感觉

## 常见坑 / 面试点

- `type=ALL` 不一定不能上线，看数据量与频率  
- 子查询不总是慢，JOIN 不总是快——以计划为准  
- 面试：如何定位一条慢 SQL；索引失效的几种情况
