# 05 · 锁

## 目标

建立 MySQL 锁的分层直觉（全局 / 表 / 行），理解与事务隔离的关系，能描述死锁与常见排查思路。

## 大纲

### 1. 为什么需要锁

- 并发写同一数据时保证正确性  
- 锁与隔离级别、MVCC 配合（细节见 InnoDB 章）

### 2. 锁的分类直觉

| 维度 | 类型 | 说明 |
|------|------|------|
| 粒度 | 全局锁 / 表锁 / 行锁 | 粒度越大并发越差 |
| 模式 | 共享锁（读）/ 排他锁（写） | `SELECT ... LOCK IN SHARE MODE` / `FOR UPDATE` |
| 意向 | 意向共享 / 意向排他 | 表级标记，服务行锁协调 |

### 3. 全局锁与表锁

- 全局：`FLUSH TABLES WITH READ LOCK`（库级只读，备份场景了解）  
- 表锁：`LOCK TABLES ... READ/WRITE`；`UNLOCK TABLES`  
- MyISAM 偏表锁；InnoDB 日常以行锁为主

### 4. 行锁（InnoDB）

```sql
START TRANSACTION;
SELECT * FROM emp WHERE id = 1 FOR UPDATE;  -- 排他锁
-- 其他事务改同一行会等待
COMMIT;
```

- 锁的是索引记录；无合适索引可能退化成更多锁甚至表级效果  
- 间隙锁 / 临键锁：与防幻读相关（概念入门，细节见 InnoDB）

### 5. 死锁直觉

- 两事务互相等待对方持有的锁  
- InnoDB 通常会检测并回滚其一  
- 减少死锁：固定加锁顺序、缩短事务、合适索引

### 6. 排查入口（了解命令）

```sql
SHOW ENGINE INNODB STATUS\G   -- 近期死锁信息等
SELECT * FROM performance_schema.data_locks;  -- 8.0
```

## 小结

- 日常业务主要关心 InnoDB **行锁** + 事务边界  
- 没索引的更新/锁定范围容易放大，拖垮并发  
- 死锁要能说清「互相等待」与「缩短事务 / 统一顺序」

## 常见坑 / 面试点

- `WHERE` 条件没命中索引 → 锁范围变大  
- 长事务持锁过久  
- 面试：乐观锁 vs 悲观锁；间隙锁解决什么问题
