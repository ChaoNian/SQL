## 1. 索引的概述

**索引**是帮助 MySQL **高效获取数据**的数据结构，可以类比为书的**目录**：先翻目录定位，再翻到对应页。

| | 没有索引 | 有索引 |
|--|----------|--------|
| 查找方式 | 全表扫描（一行行看） | 按索引定位，再取数据 |
| 读性能 | 数据量大时很慢 | 通常明显加快 |
| 代价 | — | 占磁盘空间；INSERT / UPDATE / DELETE 要维护索引，写变慢 |

**白话**：索引是用「空间 + 一点写成本」换「读得更快」。

```sql
-- 直觉：按姓名查，name 上有索引时通常更快
SELECT * FROM emp WHERE name = '张无忌';
```

## 2. 索引的结构

InnoDB 中最常用的是 **B+ 树**索引。

| 结构 | 说明 | 常见场景 |
|------|------|----------|
| **B+ 树** | 有序多路树，叶子存数据或主键；支持范围查询 | InnoDB 默认 |
| **Hash** | 等值查找快，不适合范围 | Memory 引擎等 |
| 全文索引 | 面向文本分词检索 | `FULLTEXT`（了解） |

### InnoDB 里两个重要概念

- **聚簇索引**：叶子节点存**完整行**；InnoDB 的主键就是聚簇索引  
- **二级索引（辅助索引）**：叶子存**主键值**；先找到主键，再回聚簇索引取整行 → **回表**

> 先建立直觉：「有序树定位 + 可能回表」，不必先死记页分裂细节。

---

## 3. 索引的分类

| 分类维度 | 类型 | 说明 |
|----------|------|------|
| 功能 | 主键索引 | `PRIMARY KEY`，唯一且非空；一张表一个 |
| 功能 | 唯一索引 | `UNIQUE`，值唯一，可有一个 `NULL`（视版本/定义） |
| 功能 | 普通索引 | 加快查询，无唯一约束 |
| 功能 | 全文索引 | `FULLTEXT`，文本搜索 |
| 列数 | 单列索引 | 建在一列上 |
| 列数 | 联合（复合）索引 | 多列一起建；注意**最左前缀** |
| 存储（InnoDB） | 聚簇索引 | 主键；数据按主键组织 |
| 存储（InnoDB） | 二级索引 | 非主键索引；叶子存主键 |

## 4. 索引的语法

```sql
-- 创建普通索引
CREATE INDEX idx_emp_name ON emp(name);

-- 唯一索引
CREATE UNIQUE INDEX uk_emp_idcard ON emp(idcard);

-- 联合索引
CREATE INDEX idx_emp_name_age ON emp(name, age);

-- 建表时声明
CREATE TABLE t (
  id INT PRIMARY KEY,
  name VARCHAR(50),
  idcard CHAR(18),
  INDEX idx_name (name),
  UNIQUE INDEX uk_idcard (idcard)
);

-- 查看
SHOW INDEX FROM emp;

-- 删除
DROP INDEX idx_emp_name ON emp;
-- 主键删除用：ALTER TABLE emp DROP PRIMARY KEY;（慎用）
```

## 5. SQL 性能分析

建了索引不等于用上了，要用工具确认。

### 看执行计划

```sql
EXPLAIN SELECT * FROM emp WHERE name = '张无忌';
-- MySQL 8.0 也可：
-- EXPLAIN ANALYZE SELECT * FROM emp WHERE name = '张无忌';
```

| 字段 | 关注什么 |
|------|----------|
| `type` | `ALL` 全表扫描较差；`ref` / `range` / `const` 较好 |
| `key` | 实际用到的索引；`NULL` 可能没用上 |
| `rows` | 预估扫描行数，越小越好 |
| `Extra` | `Using index` 覆盖索引；`Using filesort` / `Using temporary` 需留意 |

### 慢查询思路（了解）

- 慢日志：`slow_query_log`、`long_query_time`  
- 先抓最慢 / 最频繁的 SQL，再 `EXPLAIN`，再决定加索引或改写  

> 更系统的优化见 [03-SQL优化](./03-SQL优化.md)。

## 6. 索引使用

### 最左前缀

联合索引 `(name, age)`：

| 条件 | 通常能否较好用到索引 |
|------|----------------------|
| `WHERE name = ?` | 能 |
| `WHERE name = ? AND age = ?` | 能 |
| `WHERE age = ?` | 基本不能（跳过了最左列） |

### 回表 vs 覆盖索引

```sql
-- 可能回表：二级索引找到主键后，再回表取 * 
SELECT * FROM emp WHERE name = '张无忌';

-- 覆盖索引思路：查询列都在索引里，少回表
-- 若有索引 (name, age)，下面更易 Using index
SELECT name, age FROM emp WHERE name = '张无忌';
```

### 常见用不上索引的写法

- 在索引列上套函数：`WHERE YEAR(entrydate) = 2020`  
- 隐式类型转换：列是字符串却写成 `WHERE mobile = 13800000000`  
- `LIKE '%关键字'`（前导模糊）  
- 违背最左前缀  
- 条件区分度极低（如几乎全是同一性别）仍强行指望奇效

## 7. 索引设计原则

1. **针对高频条件建**：常出现在 `WHERE` / `JOIN` / `ORDER BY` / `GROUP BY` 的列优先考虑  
2. **区分度要高**：手机号、邮箱合适；性别单独建索引往往收益小  
3. **联合索引有顺序**：区分度高、常一起出现的列靠前；遵守最左前缀  
4. **控制数量**：索引不是越多越好，每个索引都拖慢写入  
5. **主键要短、稳**：InnoDB 主键即聚簇；避免过长 UUID 当主键（可用自增 + 业务唯一键）  
6. **覆盖常见查询**：能让热点查询走覆盖索引更好  
7. **用 EXPLAIN 验证**：加完索引看 `key` / `rows` 是否改善，避免「建了却没用」  

### 小案例

```sql
-- 业务：经常按部门查在职员工，并按入职时间排序
-- 可考虑联合索引示意（按实际 EXPLAIN 调整）
CREATE INDEX idx_emp_dept_entry ON emp(dept_id, entrydate);

SELECT id, name, entrydate
FROM emp
WHERE dept_id = 1
ORDER BY entrydate;
```

## 小结

- 索引用空间和写成本换读性能  
- InnoDB 以 B+ 树为主；主键是聚簇索引，二级索引可能回表  
- 会建/删/看索引，并用 `EXPLAIN` 确认是否用上  
- 设计抓住：高频、高区分度、最左前缀、少而精  

## 常见坑 / 面试点

- `LIKE '%xx'` 通常难以很好利用 B+ 树索引  
- 选错主键（过长、无序）影响聚簇索引效率  
- 面试：最左前缀、覆盖索引、回表、主键与聚簇索引关系
